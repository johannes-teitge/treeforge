1. Grundidee: Git als Zeitmaschine

Git speichert Zustände deines Projekts. Jeder Commit ist ein sicherer Zwischenstand. Wenn später etwas kaputtgeht, kannst du sehen, was geändert wurde, oder zu einem alten Stand zurück.

Working Tree

Deine aktuellen Dateien im Projektordner.

Staging Area

Dateien, die du für den nächsten Commit vormerkst.

Commit

Ein gespeicherter Zustand mit kurzer Beschreibung.

2. Unser TreeForge Workflow

1. Vor der Änderung prüfen

git status

Zeigt, ob Dateien geändert, neu oder bereits vorgemerkt sind.

2. Patch oder Änderung ausführen

php patches/run.php

Unser Patch-Runner führt neue Patches aus und überspringt bereits gelaufene.

3. Im Browser testen

http://treeforge.test

4. Änderungen vormerken

git add .

5. Commit erstellen

git commit -m "Add image node support"

6. Version markieren

git tag v0.1.3-alpha
Regel: Jeder Commit soll lauffähig sein. Lieber kleine Schritte als riesige Änderungen.

3. Die wichtigsten Git-Befehle

BefehlBedeutungWann nutzen?
git statusZeigt den aktuellen Zustand.Immer vor und nach Änderungen.
git add .Merkt alle Änderungen für den Commit vor.Wenn alles getestet ist.
git commit -m "..."Speichert den aktuellen Stand.Nach jeder fertigen Etappe.
git log --onelineZeigt die Commit-Historie kurz an.Zum Überblick.
git tag v0.1.3-alphaMarkiert einen Commit als Version.Nach wichtigen Meilensteinen.
git resetNimmt vorgemerkte Dateien aus der Staging Area.Wenn man versehentlich zu viel vorgemerkt hat.
git diffZeigt konkrete Änderungen in Dateien.Vor dem Commit prüfen.

Typische Reihenfolge

git status php patches/run.php git status git add . git commit -m "Kurze Beschreibung" git tag v0.1.x-alpha git log --oneline

4. Composer, vendor und .gitignore

Composer erzeugt den Ordner vendor/. Dieser Ordner gehört normalerweise nicht ins Git, weil er jederzeit über Composer neu erzeugt werden kann.

Unsere .gitignore

/vendor/ composer.phar

Composer-Autoload aktualisieren

composer dump-autoload
Wichtig: composer.lock darf ins Git. vendor/ nicht.

5. Patch-Runner verstehen

Der Patch-Runner ist unser kleines Update-System. Er sucht Dateien in patches/, führt neue Patches aus und merkt sich, welche bereits gelaufen sind.

Struktur

treeforge/ ├─ patches/ │ ├─ run.php │ ├─ executed.json │ └─ patch-003-image-node.php ├─ public/ │ └─ patches/ │ └─ index.php └─ storage/ └─ logs/ └─ patch-runner.log

Ausführen

php patches/run.php

Was passiert dabei?

  1. run.php liest executed.json.
  2. Er sucht alle Dateien patch-*.php.
  3. Bereits ausgeführte Patches werden übersprungen.
  4. Neue Patches werden ausgeführt.
  5. Ausgabe wird in storage/logs/patch-runner.log geschrieben.

Beispiel-Ausgabe

[2026-06-09 09:00:31] Patch Runner gestartet [2026-06-09 09:00:31] Starte: patch-003-image-node.php [2026-06-09 09:00:31] Datei geschrieben: app/Core/ImageNode.php [2026-06-09 09:00:31] Fertig: patch-003-image-node.php [2026-06-09 09:00:31] Patch Runner beendet

6. Tags und Versionen

Ein Tag ist wie ein Schild an einem Commit. Damit sagen wir: „Das ist Version v0.1.3-alpha“.

git tag v0.1.3-alpha

Alle Tags anzeigen

git tag

Historie mit Tags anzeigen

git log --oneline --decorate
TreeForge-Regel: Jeder kleine Meilenstein bekommt einen Alpha-Tag.

7. Häufige Probleme
